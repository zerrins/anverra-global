# Root Cause Tracing

Companion to `systematic-debugging`. Use when a bug manifests deep in the
call stack and the immediate error location is not the true source.

**Core principle:** Trace backward through the call chain until you find the
original trigger. Fix at the source, not at the symptom.

---

## When to Use

Use when:

- Error happens deep in execution, not at the entry point
- Stack trace shows a long call chain
- Unclear where invalid data originated
- A previous fix at the symptom location did not resolve the problem

---

## The Tracing Process

### 1. Observe the Symptom

Read the complete error message. Note the exact failure location.

**Backend example:**
```
org.springframework.dao.DataIntegrityViolationException:
    ERROR: null value in column "policy_id" violates not-null constraint
    at com.anverraglobal.policy.PolicyRepository.save(PolicyRepository.java:47)
```

**Frontend example:**
```
TypeError: Cannot read properties of undefined (reading 'status')
    at PolicyCard (PolicyCard.tsx:23)
```

### 2. Find the Immediate Cause

What code directly causes this?

**Backend:** Who called `PolicyRepository.save()` with a null `policyId`?

```java
// In PolicyApplicationService:
policyRepository.save(policy);  // policy.getId() is null here — why?
```

**Frontend:** Who rendered `PolicyCard` with an undefined prop?

```tsx
// In PolicyList:
<PolicyCard policy={policies[0]} />  // policies[0] is undefined — why?
```

### 3. Ask: What Called This?

Trace up the call chain one frame at a time.

**Backend — read the full stack trace bottom-up:**
```
PolicyRepository.save()          ← symptom
PolicyApplicationService.create() ← who called save?
PolicyController.createPolicy()   ← who called service.create?
```

Now look at `PolicyApplicationService.create()`: what policy object does it
build? Where does the `policyId` field get set (or not)?

**Frontend — trace the data flow:**
```
PolicyCard receives policies[0]   ← symptom (undefined)
PolicyList renders with policies  ← who provides policies?
useQuery result from API          ← what does the query return?
MSW handler response              ← what does the handler return?
```

### 4. Keep Tracing Up

Continue tracing until you find where the bad value originated.

**Backend — common origination points:**
- Missing `@Id` generation strategy on an entity
- Factory method that creates the entity without calling the ID-setting constructor
- A test that creates the entity directly via constructor instead of the factory
- Flyway sequence not created (sequence `nextval` returns null)

**Frontend — common origination points:**
- API response shape differs from the OpenAPI schema (check `openapi.json`)
- Orval-generated type expects a field that the server doesn't return yet
- React Query `select` transform returning wrong shape
- MSW handler returning wrong shape vs. real API contract

### 5. Find the Original Trigger

State it explicitly:

> "The `policyId` is null because `Policy.create()` factory uses a UUID
> generated by the application, but the test constructs a `Policy` directly
> via `new Policy()` without calling the factory. The factory is the correct
> entry point."

> "The `policies[0]` is undefined because the MSW handler returns
> `{ items: [...] }` but the component expects `{ policies: [...] }`. The
> OpenAPI schema uses `policies`, the handler uses `items`."

### 6. Fix at the Source

After tracing to the origin:

1. Apply the fix at the origination point — not at the symptom.
2. Write a test that reproduces the original failure (TDD: red first).
3. Apply the fix.
4. Verify the test passes.
5. Run the full test suite.

## Adding Stack Instrumentation

When you cannot trace manually, add temporary instrumentation:

**Backend — add diagnostic logging at each boundary:**
```java
log.debug("[TRACE] PolicyService.create entry: customerId={}, productId={}", 
    customerId, productId);

Policy policy = Policy.create(customerId, productId, ...);
log.debug("[TRACE] Policy created: id={}, status={}", 
    policy.getId(), policy.getStatus());

policyRepository.save(policy);
log.debug("[TRACE] PolicyRepository.save completed");
```

**Frontend — add diagnostic output:**
```tsx
// In the component:
console.debug('[TRACE] PolicyList render: policies=', policies);

// In a test:
screen.debug();  // Prints current DOM state

// In MSW:
server.events.on('request:start', ({ request }) => {
  console.debug('[TRACE] MSW intercepted:', request.method, request.url.pathname);
});
server.events.on('response:mocked', ({ request, response }) => {
  console.debug('[TRACE] MSW responded:', response.status);
});
```

Run once to gather evidence. Read the output. Trace from there.

**Remove all instrumentation before committing** — do not leave `[TRACE]`
logs or `console.debug` calls in committed code.

---

## Defense-in-Depth

After fixing at the root, consider whether a defensive check at the symptom
location is also warranted:

- A `@NotNull` constraint on the entity field that would have surfaced the bug
  earlier in the lifecycle
- A TypeScript type guard that makes undefined handling explicit
- An assertion in the test setup that catches future misuse

Defense-in-depth does not replace fixing the root cause — it supplements it.
